# 020 — Hooks HTTP vers le daemon plutôt qu'un process node par événement

- **Statut :** Acceptée
- **Date :** 2026-11-12
- **Décidé par :** Toi (demande d'optimisation), solution recommandée

## Contexte
Chaque session lancée par Vigie lançait `node hook.mjs` à chaque événement : avant et après chaque outil, sous-agents compris. Avec plusieurs agents, des dizaines de process par seconde. Dans l'app, ce `node` est le binaire Electron (`ELECTRON_RUN_AS_NODE`), lourd à démarrer.

## Décision
Les hooks injectés sont de type `http` : Claude Code poste l'événement à `http://127.0.0.1:<port>/api/hook`. Le daemon ajoute la même ligne au spool, lue comme avant. Repli sur `node hook.mjs` si des réglages gérés locaux posent `allowedHttpHookUrls` sans couvrir cette URL.

## Raisons
- Aucun process par événement.
- Les sessions concernées tournent dans un PTY du daemon : quand elles tournent, le daemon écoute.
- Le spool reste la seule entrée de `store.onHook` : rejeu au démarrage inchangé.

## Alternatives écartées
- Script shell à la place de node : un process quand même, et pas de JSON sans `jq`.
- Ingestion directe dans le store sans spool : deux chemins d'entrée, rejeu perdu.

## Limites
- Une politique d'organisation distante qui interdit les hooks HTTP n'est pas détectée : l'état temps réel serait coupé (les transcripts restent lus).
- La statusline relais lance encore un process par rafraîchissement (pas de type HTTP pour la statusline).
