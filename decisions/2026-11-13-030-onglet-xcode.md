# 030 — Onglet Xcode : schemes, simulateurs, build / test / run, scripts du projet

- **Statut :** Acceptée
- **Date :** 2026-11-13
- **Décidé par :** Toi (plan validé)

## Contexte
Pour une session ouverte sur un projet iOS, construire, tester ou lancer l'app sur un simulateur oblige à quitter Vigie pour Xcode ou un terminal. L'onglet Xcode le fait depuis la session : choix du scheme et du simulateur, actions dans un terminal Vigie, ouverture dans Xcode, scripts `scripts/*.sh|*.py` du projet.

## Décision
- Adaptateur `daemon/xcode.mjs` (comme `mise.mjs`) : `execFile` sans shell, stdin fermé, environnement `cleanEnv`, ne rejette jamais. Routes `GET …/xcode` (conteneur + scripts, sans process), `GET …/xcode/targets` (schemes + simulateurs), `POST …/xcode/open` (`xed`), et `xcode` / `script` dans `POST …/terminals`.
- **Frontière de plateforme par la disponibilité de l'outil**, pas par `process.platform` : `xcodebuild` ou `xcrun` introuvable (Linux) ou qui répond « requires Xcode » / « unable to find utility » (Mac avec les seuls Command Line Tools) → `available: false`. Aucun point de plateforme à ajouter : le même code tourne partout, les tests utilisent de faux exécutables et passent sous macOS comme sous Linux.
- **DerivedData de Vigie sous `~/.vigie/xcode/<sha256(cwd)[0:12]>`** (`-derivedDataPath`) : rien n'est écrit dans le DerivedData d'Xcode ni dans le projet ; on retrouve ses builds d'un lancement à l'autre.
- **Scheme validé par regex + `shQuote`, sans relecture de la liste** : le contrat refuse un scheme vide, en `-…` (pris pour une option) ou avec un caractère de contrôle ; la commande le passe quoté. Relire `xcodebuild -list` à chaque clic coûterait plusieurs secondes. Le conteneur, lui, est relu (une `readdir`), et un script n'est lancé que s'il figure dans `scripts/` relu à l'instant.
- `run` passe par `/bin/sh -c '<script fixe>' vigie <scheme> <udid> <derivedData> <conteneur>` : le PTY exécute `$SHELL -l -c`, et fish ne comprend pas `VAR=$(…)`.

## Raisons
- Tester l'OS dirait « macOS » sur une machine sans Xcode ; c'est l'outil qui sait s'il peut servir.
- Un DerivedData propre évite de casser l'indexation ou le build en cours dans Xcode.
- La regex et le quotage suffisent contre l'injection ; xcodebuild refuse lui-même un scheme inconnu.

## Alternatives écartées
- Brancher sur `process.platform` : faux positif sur un Mac avec les seuls Command Line Tools.
- Relire la liste des schemes avant chaque action, ou la mettre en cache dans le daemon : lent, ou un état de plus à invalider ; l'UI garde la liste.
- Résoudre le chemin de l'app via `-showBuildSettings -json` : un appel de plus à chaque run ; on suppose `Debug-iphonesimulator` et on prend le premier `.app`.

## Conséquences
- `~/.vigie/xcode` grossit avec les builds ; à nettoyer à la main (ou via l'action `clean`).
- watchOS, tvOS et visionOS ne sont pas proposés ; un projet à plusieurs conteneurs ouvre le premier par ordre alphabétique.
